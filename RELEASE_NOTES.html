October 25, 2026

Release date: October 25, 2026 · v3.4.20 – v3.4.21

New features and updates to existing features in the Data Dictionary:

  • Field history: a month is read from its biggest batch first, as the notes for v3.4.17 said it was (beta).
  • Check by hand: every field carries a Query Service statement, ready to paste, that shows the operator the data for themselves.

Check by hand

The dictionary's coverage and history come from sampling batches. Whoever runs it sometimes needs to see the data directly -- to confirm a surprising figure, or to answer a question the sample cannot.

New features

FeatureDescription
Check by hand (SQL) New
v3.4.21		The last column of the Field Index and every schema tab: one read-only Query Service statement for the field, on one line so it pastes cleanly out of Excel. For an event field it counts records, records carrying the field and the % filled per event month in each of the schema's tables; for a Profile record field, the same across the default merge policy's Profile snapshot table -- what an audience sees now; for a lookup or other record data, across each table's records in the data lake. Arrays are searched with exists(), so products[].gtin means "some product has a GTIN". Each statement is labelled /* Data Dictionary: … */ for the Query Service log.

Field history

The first full run on UK prod called 150 dataset-months data-lake files empty. The independent check re-read 60 of them and found rows in 4. The "biggest first" step asked Catalog for a month's 100 biggest batches -- and then read the four nearest their median size. On ROI prod that is close to the biggest. On UK prod a profile dataset's month holds about 2,400 batches, and the median of its biggest 100 is a few hundred records: small loads whose data-lake files are empty, while the daily load of 34.5 million records at the top of the list was never tried.

Fixes and improvements

FixDescription
Biggest batch first Fixed
v3.4.20		The biggest batches of a month are now read biggest first. The typical newer batch read beside it is unchanged.
Only the doubtful months re-read Updated
v3.4.20		The order could change only a data-lake files empty verdict, so a cache written by v3.4.18 – v3.4.19 keeps every other month and reads just those again: minutes, not the hours of a cold run.

For more information, read the README.

October 24, 2026

Release date: October 24, 2026 · v3.4.15 – v3.4.19

New features and updates to existing features in the Data Dictionary:

  • Field history: the cause of its timeouts found and removed, and every month it cannot read now explained (beta).
  • In Profile now: how much of each field an audience can actually see, given the Profile retention on its dataset (beta).
  • Coverage: a schema whose data went to Profile is no longer called "genuinely not populated".

In Profile now

Audiences are built on Profile, not the data lake, and Profile keeps event data only as long as the Profile retention set on each dataset -- which is not the same everywhere. On ROI prod most event datasets keep 90 days, but the order events dataset keeps 45 and promotion interactions 60, while their data lake copies go back two years. A "bought in the last 90 days" audience on order events can only see 45 of them, however far back the lake goes.

New features

FeatureDescription
In Profile now (days) New Beta
v3.4.16		Two columns beside "Have we got it?" on the Field Index and every schema tab (and the days on the Field History tab): the field's days of unbroken data, capped by the Profile retention of the dataset that carries it, with the reason in words -- all 90 days Profile keeps, Profile keeps only 45 days (&lt;the order events dataset&gt;), 24 of the 90 days Profile keeps -- since 30 Sep 2026. Worked out dataset by dataset, so a backup dataset with a longer retention but one month of data cannot lend its retention to another dataset's long run.
Profile retention on the Summary New
v3.4.16		Every Profile-enabled dataset with a Profile retention, how many days Profile keeps and how long the data lake keeps; under 90 days in red.

Field history

The first full ROI prod run of --history took 5 h 15 min, and 656 of its 1,227 Data Access file lists ended in 504 Gateway Timeout at exactly 60 s. It was not a bad night at Adobe. Every one of the 328 batches behind those timeouts was the Profile-side half of a batch ingestion: Catalog lists it as an ordinary successful batch of the dataset, but it has no data-lake files, and Data Access hangs until the gateway gives up instead of saying so. The same batches still timed out the next morning, and on retry 30 s and 90 s later; the datasets' data-lake batches read in seconds.

Fixes and improvements

FixDescription
Profile-side batches skipped Fixed
v3.4.15		A batch with an old-style 24-character id and Profile write metrics (records read / written, profile fragments, no file counts) is no longer read, in history or in coverage sampling -- the same way consolidation batches are already skipped. Each one cost two minutes of waiting.
"Profile only" months New
v3.4.15		A month that holds nothing but Profile-side batches is marked at once -- Profile only: no data-lake copy to read -- instead of being read. It still shows as ?, and the schema tab names the datasets it affects.
Only the fixable months are retried Updated
v3.4.15		A month that can never be read -- Profile only, empty files, or files Adobe has deleted (HTTP 404) -- is now cached like any finished month. Only a timeout or 5xx is asked again next run. The log says how many will be.
Batches with a known size first Updated
v3.4.15		Within a month, batches whose record count Catalog knows are tried before those it doesn't, which are more often empty.
Every unreadable month explained Fixed
v3.4.16		After v3.4.15, 126 dataset-months on ROI prod still showed ?. Each kind was traced: (1) data-lake files that really hold no rows -- a 970 MB load into the product lookup left a 4 KB, zero-row file, because the records went to Profile -- now labelled data-lake files empty; (2) the identity service's …-INGEST marker batches, whose file list Data Access answers with DTAC-4043 DataSetFile not found, now skipped like Profile-side ones; (3) months whose readable batches were hidden: only the newest 10 batches of a month were asked for, and in a busy month those can all be Profile-side or empty.
A month's batches, 100 at a time Updated
v3.4.16		Catalog is asked for 100 batches per month instead of 10, paging back up to five pages when the first holds nothing readable, and up to four batches are tried when files come back empty (each such read takes about two seconds). A Profile-only month now records how many records Profile received, and the schema tab says so.
Earlier caches re-checked Updated
v3.4.16		Months cached by earlier versions were judged from 10 batches, so they are not trusted: the first v3.4.16 run reads every month again.
Checked against Adobe a second way Fixed
v3.4.17		An independent check re-asked Adobe about the v3.4.16 ROI prod verdicts a different way -- every batch of each "Profile only" month, other batches of "data-lake files empty" months, Catalog's own oldest batch for each "data since" date. 34 of 36 held. The two that did not were semi-smart coupon months of about 1,480 batches whose three readable batches sat past the fifth page. Each month is now first asked for its batches biggest first (Catalog sorts on the record count), which shows the readable ones in one call however many batches the month holds; the page-by-page walk runs only when nothing has records. The coupon dataset now reads unbroken since December 2025. Months cached by v3.4.16 are read again.
Two batches a month Updated
v3.4.18		Comparing the newest-first (v3.4.16) and biggest-first (v3.4.17) runs month by month showed what each misses. On some datasets the biggest batches, counted as one record, hold empty files while a newer batch has the rows, so when every biggest batch is empty the month is walked newest first as well. And one batch a month missed rarely-filled fields in 21 of about 400 months -- a miss that can look like a break in the field's run -- so the biggest batch and one typical newer batch are both read, and the fields counted across the two.

Coverage

Fixes and improvements

FixDescription
No more false "genuinely not populated" Fixed
v3.4.19		Coverage sampled a dataset's newest 20 batches. When those were all Profile-side or empty -- the Marketplace Order Event datasets on ROI prod have thousands of empty data-lake batches -- the schema was reported as EMPTY, "genuinely not populated". Now, when the newest 20 give nothing, the biggest batches of the last 90 days are tried as well, and a schema that still yields nothing is named for what it is: Profile only (its datasets load to Profile, with no data-lake copy to sample) or data-lake files empty (batches report records, but their files hold none). Both read coverage unknown, not 0% in the DATA COMPLETENESS block, and neither is reported as a read failure any more. "Empty" now says what was checked.

October 23, 2026

Release date: October 23, 2026 · v3.4.14

New features and updates to existing features in the Data Dictionary:

  • Field history: fixes from its first full prod run (beta).
  • Running the dictionary: every pass ends with an Adobe endpoint health report.

Field history

The first full prod run of --history took seven hours, of which six were the history pass; 38% of months could not be read and 12 datasets were lost outright. Adobe's Data Access file lists were slow all morning, but the engine made it worse than it had to be.

Fixes and improvements

FixDescription
No dataset lost to one timeout Fixed
v3.4.14		Each dataset began by asking Catalog for its oldest batch. On very large datasets that sort returned 504 Gateway Timeout, and the whole dataset was given up -- 12 in prod, including the Analytics feed and every orders and returns dataset. Months are now walked with Catalog's newest-first query bounded to the month, which answers in about 0.2 s, and the exact start date is looked up only inside the first month that has data.
One file list per read Updated
v3.4.14		The reader fetched a file list for up to 40 files of a batch before choosing one; history needs one. It now asks for one, and waits 90 s for it instead of 30: the first request for a batch's file list was measured at 17.8 s and often passed 30 s, while the repeat took 0.6 s.
Locked datasets skipped Updated
v3.4.14		A dataset Data Access refuses outright (HTTP 403, e.g. the semi-smart coupon dataset) is recognised on its first read and skipped, with the reason on its schema tab, instead of being retried month after month.
Back-off when Adobe struggles New
v3.4.14		When most of the last 20 Data Access calls time out or return 5xx, every history worker pauses for three minutes rather than piling up unreadable months. Unreadable months are never cached, so the next run retries them.

Running the dictionary

New features

FeatureDescription
Adobe endpoint health New
v3.4.14		Every request is counted per Adobe endpoint (Catalog, Data Access file lists, downloads, Schema Registry, Profile). The run log shows a health table after the schema and coverage passes and after history: calls, failures by kind (no answer in time, HTTP 504 ...), median, 95th percentile and slowest response. Retry messages now name the endpoint and the reason, e.g. Data Access file list ...: no answer in 90s; retry 2/2.

For more information, read the README.

October 22, 2026

Release date: October 22, 2026 · v3.4.12 – v3.4.13

New features and updates to existing features in the Data Dictionary:

  • Field history: how many months of unbroken data each field has, for building audiences (beta).
  • Sample values: the top 10 instead of the top 5, with personal data starred.

Field history

Coverage % says how often a field is filled in now. Building an audience also needs to know how far back the field goes: a "purchased in the last 12 months" audience is no good on a field that has only been arriving for six weeks.

New features

FeatureDescription
"Have we got it?" Beta
v3.4.13		--history adds three columns to the end of the Field Index and every schema tab: months of unbroken data up to now, a plain-English detail (since 28 Sep 2026, stopped -- last seen Aug 2026, since May 2026 -- missing in Apr 2026) and a heartbeat, one bar per month, oldest first: ░ no data at all, ▁ data arrived but the field was empty, ▂ to █ how often it was filled, ? could not be checked. The start is the real date where it is known (the dataset's first batch, or the edge of its TTL), not a whole month. In prod the slot expiry fields read <1 (first batch September 28) while order events go back to April 2025.
Field History tab Beta
v3.4.13		The same months as columns, the % of sampled records carrying each field, shaded green. Blank is no data at all that month, 0 is data without the field.

How it works. Querying each field month by month in Query Service would mean a query per field per month. Instead, for each dataset and month, Catalog finds that month's batches (createdAfter / createdBefore, about 0.2 s) and one of them is read through the Data Access API with the coverage pass's reader. That one download answers for every field at once, so the cost is datasets × months, not fields × months; months before a dataset's first batch, or past its TTL, cost nothing. Test, perf and temp datasets are left out so they cannot make a field look older than the real feed. Finished months are cached locally in output/field_history_cache/, so only the first run on a sandbox is long.

Known issues

IssueDescription
A sample can missEach month is judged from one to three batches, not every record. One sample a month faked a gap in testing (April's order sample was an odd 101-row batch carrying 9 of 16 fields), so a month that is thin, short of fields or missing a well-filled field both neighbours have is sampled again from earlier in the month. A rarely-filled field's one-month hole is shown as ? rather than a break.
Months go by load dateHistory follows when data was loaded. Events backfilled later count from the load; the schema tab says when a sample showed events much older than their batch.
The first run is longEvery month of every dataset is read once: hours on a big sandbox. Later runs read only the current month.

Sample values

Updates

UpdateDescription
Top 10 values Updated
v3.4.12		The sample columns show the ten commonest values instead of five.
Personal data starred New
v3.4.12		Email addresses (by value) and identifier / contact fields (by name: user id, CRM id, ECID, phone and the like) have two characters starred before they are counted, whether or not the field carries a DULE label: j**n.doe@acme.com. The shape and the ranking survive; a whole real identifier does not. A How to Use row says so.

The schemas the filters drop are now accounted for in the workbook itself, on two hidden tabs (right-click any tab › Unhide). v3.4.8's bug went unseen because a dropped schema left no trace: its reason was printed to the console and then gone.

FeatureDescription

Running the dictionary

Fixes and improvements

FixDescription
The run keeps the PC awake Updated
v3.4.11		On October 16 the machine went into Modern Standby part-way through prod's run and froze it for 76 minutes (18:43 to 20:01). Nothing failed; it simply stopped. October 6, 2026

Release date: October 6, 2026 · v3.4.6

New features and updates to existing features in the Data Dictionary:

  • Audiences: a complexity score for every rule-based audience.

Audiences

Not all audiences are created equal: one badly built audience can double the nightly batch run on its own, and AEP's own metrics never say what an audience cost to compute.

New features

FeatureDescription
Audience complexity score New BetaThe Audiences tab gains a Complexity score (0-100) and a RED / AMBER / GREEN on it, plus the reasons: Why this score (the points, in plain English), event scan, lookback days, lookup joins, joined fields, aggregations, depends-on count, largest base audience and its size, sequence steps, conditions, longest hard-coded value list, merge policies, and how many audiences use it. The run log reports the RED / AMBER / GREEN counts per sandbox. The How to Use tab explains the score and the usual fix: shorten the lookback, or move the sum / count upstream into a computed attribute.

How the score is built

The rules follow the two miaprova.com write-ups on expensive AEP segments (Why your most expensive AEP audience might be your newest one; The right fix for expensive AEP segments: move the math upstream). Each cost driver is read off the PQL and the audience record.

Cost driverPoints
Event scan and lookbackThe longer the window, the more events are read per profile per night. A scan with no time limit scores highest (35).
Lookup joinsA join to another class (products via gtin) runs per event per profile: 18, +4 per extra field, capped at 25.
Aggregations that cannot short-circuitsum / average 15, count 10, "occurs N times" 6, forall 4, capped at 20.
Base audience sizeinSegment() on a big audience scans all of it: +2 per dependency, +3 / +6 / +9 for a base of 1M / 5M / 20M profiles.
Smaller signalsSequences, condition count, lists of 100+ values, more than one merge policy, a negated event step and an overridden performance warning.

RED is 55 and over, AMBER 30 to 54. The weights live in audience_complexity.py (developed standalone, folded in) and are a first cut to be argued with. The size of each base audience is read from /segment/definitions/<id> once per run (a few hundred small reads).

Note

First prod run: 2,205 rule-based audiences scored: 64 RED, 482 AMBER, 1,659 GREEN. Every RED is the same shape: an unlimited event scan, a product lookup join, and a base audience of 13 to 23 million profiles.

For more information, read the README.

September 21, 2026

Release date: September 21, 2026 · v3.4.2

New features and updates to existing features in the Data Dictionary:

  • Workbook: a tab colour system that means something; data-hygiene columns.
  • Coverage sampling: honest completeness statuses.

Workbook

Purple used to mean only "built on the XDM Individual Profile class". A Profile-class schema whose datasets were all disabled for Unified Profile was still purple (five tabs in a prod run: raw feeds, backups, pattern experiments) and, worse, its coverage was sampled from the Profile Snapshot Export, where its rows never land, so it read as empty.

New features

FeatureDescription
Tab colour system UpdatedEvery schema tab is coloured on two axes: the hue is the class, the shade is whether the data reaches Unified Profile (see the table below). "In Profile" is read from each dataset's tags.unifiedProfile, the same signal the Datasets tab's Profile column shows. Only dark purple schemas are in the merged union and sample coverage from the Profile Snapshot Export; every other schema samples its own datasets (the tab header's source: note says which). A six-swatch colour key at the top of the Summary tab explains the system.

August 14, 2026

Release date: August 14, 2026 · v3.4.0 – v3.4.1

New features and updates to existing features in the Data Dictionary:

  • Coverage sampling: complete coverage on Profile schemas.
  • Workbook: the credential name is gone from the workbook; release notes are linked from it.

Coverage sampling

A prod run came back with 16 of 33 schema tabs flagged MISSING. All 16 were Profile-class, and all 16 failed for one reason: a single gateway 504. Every Profile-class schema samples the same Profile Snapshot Export union, but each one re-downloaded the ~127 MB partition for itself: sixteen downloads of identical data, and sixteen chances to hit a 504. The snap_unreadable cache added in v3.2 refused to retry a snapshot that had already failed, so the first failure became MISSING coverage for every Profile schema behind it.

Fixes and improvements

FixDescription
One snapshot download per sandbox Fixed
v3.4.1		The snapshot is sampled once per sandbox and the rows reused in memory for every Profile-class schema. One download, not sixteen. In the log, Profile schemas after the first say reusing the snapshot sample already downloaded this run (N rows, no re-download).
Retry pass New
v3.4.1		At the end of sampling, any schema still UNREADABLE is tried once more before the workbook is written, with the snapshot cache cleared so the union gets a genuine second attempt. It costs nothing when the first pass was clean, and announces itself in the log as RETRY PASS.
Sampling errors are classified Fixed
v3.4.1		A sampling exception is now unreadable rather than falling through unlabelled, so it lands in the DATA COMPLETENESS block instead of reading as "not sampled".

Workbook

Titles inside the file used to fall back to the credential's service name, the key under which a credential is filed in the OS vault. A workbook read with a key stored as <name> was headed "Data Dictionary — <Name>", putting an artefact of our own key management exactly where the reader expects the subject of the report. It also implied the wrong thing: the credential says who read the sandbox, not what the document is about.

Fixes and improvements

FixDescription
The credential name is gone Fixed
v3.4.0		Workbook titles use a client name only when the credential record carries an explicit client key. With no client configured, every title identifies the workbook by sandbox, the same thing the filename has said since v3.3: a prod run is headed "Data Dictionary v3.4.0 — prod". This applies to all four titled tabs: Summary, Field Index, Datasets, Audiences. The console banner still names the credential set, which is operationally useful and never leaves your machine.
Release notes are linked New
v3.4.0		The provenance line on every tab ends with a link to this page, and the How to Use tab gains a clickable "What's new in v3.4.0" link.

Important

To show a real client name in the titles, add a client key to that credential record. Otherwise you get the sandbox, which is usually what you wanted anyway.

Note

Reading coverage. Coverage is sampled from up to --dd-rows records (default 1000), not the whole dataset: it means roughly how often this is populated, not an exact figure. Busy datasets make Catalog time out when asked to sort every batch they have ever held, so the tool filters status=success server-side and steps the page size down (20 → 5 → 1) rather than giving up; a narrower sample beats no coverage, and the log says when it happens. Adobe's own consolidation batches are skipped: Catalog advertises them with the combined record count, but the Data Access API refuses them outright (DTAC-4000). Nothing is lost, because the batches they absorbed are still served individually.
